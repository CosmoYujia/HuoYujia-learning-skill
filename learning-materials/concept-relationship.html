Agent × 大模型上下文 × Skill：三者是什么关系？

把"执行者、工作台、作业手册"放到一起，看清它们如何配合完成一件复杂的事
📚 主题：Agentic AI 概念关系 ｜ 更新：2026-09-06 ｜ 依据：基于已交叉验证的权威资料（Anthropic 官方、skill.md 标准、IBM 等）整理

1开篇总述：三个角色，一台戏

如果把一件复杂任务的完成比作一次"专家上门作业"，那么三者的分工非常清晰： Agent（执行者）负责拆目标、做决策、调工具、把事办成； 大模型上下文（工作台）是它一次作业里能摊开的全部信息，决定"当下看得见、记得住多少"； Skill（作业手册）是把"这类事该怎么规范地做"提前写成的可复用手册，让执行者下次不用从头摸索。

三者不是并列的三样东西，而是同一套智能体系统里层层嵌套的三个环节：Skill 把"该怎么做"的知识喂给上下文，上下文框定 Agent 当次能看到与用到的范围，Agent 则在这个范围里调用 Skill 与工具去达成目标。把一句话拆透，就能理解它们关系的全部。

2分点讲解

2.1三者的整体协作关系

一次完整任务的执行，是一个"由 Skill 供给流程、由上下文承载信息、由 Agent 驱动循环"的协作流水线，典型顺序如下：

1
会话启动，Agent 的"大脑"里已有一份轻量目录：系统提示中常驻着所有已安装 Skill 的 name 与 description（元数据，每个约 100 token）。
2
用户提出请求，Agent 判断它与某个 Skill 的 description 是否匹配——这决定了"要不要翻开这本手册"。
3
触发后，Agent 把该 Skill 的 SKILL.md 正文（流程指令）读入上下文，必要时再按需读取 references/、执行 scripts/。
4
Agent 进入"感知—推理—行动—观察"（ReAct）循环：结合上下文中的任务信息、工具结果，一步步推进直到目标达成或触发停止条件。

换句话说：Skill 是"剧本"，上下文是"舞台能摆下的道具"，Agent 是"照着剧本在舞台上走位、把戏演完的演员"。没有剧本（Skill），演员每次只能临场发挥；舞台太小（窗口不够），再好的剧本也施展不开。

2.2上下文如何影响 Agent 的工作效果

上下文窗口 ≈ Agent 的"工作记忆"。它决定一次请求中 Agent 能同时考虑多少信息（以 Token 计），直接影响任务效果的好坏：

  • 装得下的信息 → 才用得上：当 prompt、文档、对话历史、Skill 指令总和超出窗口时，要么请求被拒（"Context window exceeded"），要么被迫截断/摘要——该有的关键信息可能丢失。
  • 输入会挤占输出：输入与输出共享同一个窗口，塞太满会压缩可用输出空间，导致回答被截断。
  • 大 ≠ 一定好用：关键信息放上下文中间时，模型容易"遗忘"（Lost in the Middle）；无关信息太多会稀释注意力（上下文腐烂），甚至诱发幻觉。所以"堆料"式地把海量资料塞进去，常常适得其反。

对 Agent 的三个直接影响：

  • 决定任务能不能做——一个需要读完整代码库或长文档的任务，窗口太小就做不了。
  • 决定做得准不准——信息组织得好、信噪比高，Agent 更少漏事实、更少幻觉。
  • 决定成本与速度——上下文越长，自注意力的计算与 KV 缓存开销越大，越慢越贵。

因此工程上通过 截断、摘要压缩、滑窗、RAG 检索等手段"管理上下文"，本质都是为了让 Agent 在有限的窗口里，尽可能用到最相关、最该用的信息。

2.3Skill 如何沉淀可复用的任务知识

Agent 每完成一次任务，经验往往随会话结束而"清零"（上下文是短期工作记忆）。Skill 解决的正是"如何让经验留存、复用、分发"：

  • 把"怎么做"固化下来：把重复任务的步骤、判断规则、验收标准、禁止项写成 SKILL.md，连同脚本/参考/资源放进一个文件夹，形成标准作业程序（SOP）。
  • 用渐进式披露省上下文：Skill 平时只占几十~一百 token 的元数据；只在被触发时才加载正文，从而让 Agent 可以"带很多手册"却不撑爆工作记忆。
  • 一次封装、处处复用：做成开放格式后，可在多个支持该标准的智能体间复用、用 git 版本管理并与团队共享——从"个人经验"变成"团队资产"。

Skill 与上下文的关系很微妙：Skill 既依赖上下文（它的正文要被读入窗口才会生效），又反向优化上下文（通过分层、按需加载，把"塞进窗口的内容"压到最小、最相关）。这正是它能在长流程任务中发挥作用的关键。

一句话记忆：Skill 把"容易忘、该规范的流程知识"沉淀成可复用的手册；这份手册要借助上下文才能生效，而 Agent 则是那个按手册在上下文舞台上把事做成的主体。

3三者核心维度对比

对比维度 Agent（执行者） 大模型上下文（工作台） Skill（作业手册）
本质 能感知、决策、行动的系统 单次请求内能考虑的信息量上限 可复用流程知识与资源的文件夹格式
回答的问题 这次怎么把目标做成 当下能看见/记住多少 这类任务按哪套流程规范地做
可复用性 会话内动态决策，不长期保留经验 短时工作记忆，用完即清 跨会话、跨产品可复用（按需加载）
记忆属性 靠记忆模块延续 短期记忆 外部持久化的"程序性知识"
对"信息量"的态度 在窗口约束下做取舍 有硬上限，输入输出共享 用分层把载入量压到最小
主要载体/体现 模型 + 工具 + 执行循环(ReAct) 窗口中的 prompt、历史、文档、注入内容 SKILL.md + scripts/ + references/ + assets/
相互依赖 依赖上下文获知信息、依赖 Skill 获得流程 承载 Skill 指令，约束 Agent 能力范围 正文须读入上下文才生效，由 Agent 触发执行

4总结

三者是一个层层支撑的整体：Agent 是主体，负责用目标驱动的循环把事办成；上下文是 Agent 的"工作记忆/舞台"，其容量与信息质量直接决定 Agent 能做多长、多准、多省的任务——所以必须被主动管理（RAG、摘要、按需注入）；Skill 是"沉淀下来的手册"，通过渐进式披露，把可复用的流程知识装进 Agent 的上下文而不挤占它，从而把通用 Agent 变成稳定的"专家"。

三者缺一不可：没有 Skill，Agent 每做一类事都要人重新交代、且容易出错；不懂上下文，再强的 Agent 也会因塞不下、记不牢或堆料稀释而效果崩塌；没有 Agent，手册与舞台都只是静止的资源，无人去真正执行。

理解这三者的关系，也就抓住了当下 Agentic AI 应用设计的核心：让会执行的 Agent、有限的上下文、可沉淀的 Skill 恰到好处地协同。
