3概念解释 Concept Explanation

一句话定义

Agent Skill（智能体技能），是把程序性知识（怎么做事）与相关资源，组织进一个可被发现、按需加载的文件夹，从而把一个"通用智能体"变成"擅长特定任务的专家"的开放能力格式。

通俗类比

把一个 Skill 想成给新员工做的一份入职指南（onboarding guide）：它不讲"你是谁"这种通用事（那属于系统提示），而是聚焦"如何把这项工作做好"。员工（智能体）平时只需知道手边有哪几份指南（只读标题）；当任务对上了某份指南，才翻开正文照着做；若需要更细的操作手册或工具脚本，再按需查阅。

权威定义与出处

① Anthropic 官方工程博客：Agent Skills 是"有组织的指令、脚本与资源文件夹，智能体可动态发现并按需加载，从而在特定任务上表现更好"的能力。它把专家经验封装成可组合（composable）的能力，把通用智能体变成贴合需求的专用智能体。

② Agent Skills 开放标准官网（skill.md）：Agent Skills 是一种轻量、开放的能力格式，用于为 AI 智能体扩展专业知识与工作流。其核心是"一个含 SKILL.md 的文件夹"，该文件至少包含元数据（name 与 description）与指示智能体如何完成任务的说明；还可附带脚本、参考资料、模板等。

③ Anthropic 官方产品文档（platform.claude.com）：Skills 是"可复用的、基于文件系统的资源"，赋予智能体领域专业知识（工作流、上下文与最佳实践）。与"针对一次性任务的对话级 prompt"不同，Skill 按需加载，无需在每次对话中重复相同的指导。2025-12-18 起，Agent Skills 被发布为开放标准，实现跨平台可移植。

历史脉络：Agent Skill 由 Anthropic 提出并开源标准化，2025 年 12 月发布为开放标准后被大量智能体产品与客户端采用，形成 skill.md 生态。它是一个"仍在快速演进"的新兴规范。

4核心机制 Core Mechanism

4.1 目录结构

一个 Skill 本质上是一个文件夹。最小形态只含一个 SKILL.md；复杂时可在其中捆绑额外文件：

my-skill/
├── SKILL.md        # 必需：元数据(YAML frontmatter) + 正文指令
├── scripts/        # 可选：可执行代码（Python/Shell/JS 等）
├── references/     # 可选：参考文档（API 文档、Schema、政策等）
├── assets/         # 可选：模板、资源文件
└── ...             # 任意其他文件或子目录

4.2 SKILL.md 的结构

顶部：YAML Frontmatter（元数据）——Skill 的"身份证"，至少包含 name 与 description。description 极其关键，它是智能体把"用户请求"与"该不该触发这个 Skill"进行匹配的依据，因此既要说"这个 Skill 做什么"，也要说"什么时候用它"。

---
name: pdf-processing
description: 从 PDF 提取文本与表格、填写表单、合并文档。当处理 PDF 文件或用户提到 PDF/表单/文档提取时使用。
---

正文：程序性指令——用 Markdown 写明"怎么做"，通常包含：必需输入、有序步骤、判断规则、期望输出、失败/升级条件、验证动作、明确禁止的动作。推荐将 SKILL.md 保持精简（官方建议 500 行以内），把细节移到引用文件。

4.3 核心设计原则：渐进式披露（Progressive Disclosure）

这是让 Skill"既强大又不撑爆上下文"的关键，内容分三层，各在不同时机、以不同 token 成本进入上下文：

层级加载时机成本内容
L1 元数据启动时始终加载每个 Skill 约 100 token所有已安装 Skill 的 name + description 进入系统提示，让智能体知道"何时该用哪个"。
L2 指令Skill 被触发时通常 <5K token智能体认为相关时，才读取完整 SKILL.md 正文进上下文。
L3+ 资源与代码需要时才访问访问前为 0references/、assets/、scripts/ 等捆绑文件，按需读取或执行。

由此带来的好处：可以安装大量 Skill 而不产生上下文负担——在真正被触发前，每个 Skill 只占几十~一百 token 的元数据。可捆绑的上下文量因此"几乎不受限"。

4.4 Skill 如何"跑起来"

典型调用链（以读取一个技能为例）：

  1. 会话启动：系统提示中含各 Skill 的 name/description。
  2. 用户请求到来，智能体判断与某 Skill 的 description 匹配。
  3. 智能体用文件/代码执行工具读取该 Skill 的 SKILL.md 正文进上下文。
  4. 按正文指示，必要时继续读取 references、执行 scripts（某些操作用确定性代码比"让模型生成 token"更可靠、更省成本）。
  5. 按指示完成任务并产出结果。

4.5 Skill 与相邻概念的分工

机制它回答什么适合
Prompt这一次具体要做什么一次性/临时任务。不可复用、无发现机制。
Custom Instructions / AGENTS.md几乎每次都适用的规则始终加载的通用默认行为、仓库级长期规则。
Agent Skill这类任务按哪套流程/知识/边界做可复用、按需加载的流程知识包。
Script（脚本）如何做确定性转换/检查精确计算、校验、文件操作；但不能"解释何时用"。可被 Skill 捆绑。
MCP Server能连上哪些外部系统/实时数据访问实时/外部数据（数据库、API），需要连接与授权。
Plugin如何分发与安装安装与共享的打包层，可把 Skill、MCP、commands 等打包在一起。

一句话厘清几个关键对：MCP 提供"能连到什么"，Skill 提供"该怎么做事"——二者正交且常组合（MCP 取数，Skill 教模型按团队规范处理这些数）。Skill 更像"自动触发的标准作业流程（SOP）"，斜杠命令（Slash Command）则是"手动触发的流程"。Plugin 是分发容器，不是流程本身。

5应用场景 Applications

场景 A：文档处理技能（官方内置示例）

  • 怎么用：把"从 PDF 提文本/填表单/合并"的步骤封装成 skill，模型读 SKILL.md 与 forms.md、必要时跑脚本。
  • 为何有效：模型懂 PDF 内容但不会"直接操作"，Skill 恰好补上程序性操作能力；表单细节放引用文件，保持核心精简。

场景 B：团队代码评审规范

  • 怎么用：把"按团队标准评审 PR"的方法做成 skill；配合 MCP 取到 PR 数据。
  • 为何有效：MCP 提供"PR #402 内容"，Skill 教模型"用团队规范审它"——访问与流程解耦、各司其职。

场景 C：重复性内容/研报/合规流程

  • 怎么用：把"从提交记录生成面向客户的发布说明""按品牌规范审阅营销内容""按合规清单审查"等做成 skill。
  • 为何有效：任务重复、输出结构稳定、步骤易被遗忘——正是 Skill 的理想对象，能保证一致、可审计。

场景 D：跨产品复用与团队共享

  • 怎么用：做成开放格式的 skill 后，在支持该标准的各智能体客户端间复用，或用 git 版本控制与团队共享。
  • 为何有效：可组合 + 可移植 + 高效（只加载所需），把个人/团队经验沉淀为可分发资产。

6易混淆问题 Confusions

易混概念区别要点
Prompt
vs
Skill		 Prompt 是一次性对话指令，无结构化、无自动发现；Skill 是结构化、可发现、可复用的能力包，按需加载。判据：同一段指令你写/贴了 2 次以上 → 可能是 Skill 的候选。
Custom Instructions / AGENTS.md
vs
Skill		 前者是几乎总适用的宽泛偏好与仓库级规则，常驻上下文；Skill 是任务特定的详细流程，只在相关时进入上下文。宽泛指南→自定义指令；具体 SOP→Skill。
Skill
vs
Script（脚本）		 Skill 定义"何时做、按什么流程做、失败了怎样"；Script 只做确定性转换/计算，不能解释用途。官方建议：默认用指令，仅当需要确定性时再加脚本，并把脚本捆绑进 Skill。
Skill
vs
MCP Server		 Skill 提供"如何做（procedure）"，静态、无需连接；MCP 提供"能访问什么（access）"，连实时外部系统、需授权。二者互补：MCP 取数、Skill 教用法。
Skill
vs
Plugin		 Plugin 是分发/安装层，可把 Skill、MCP、Slash Command 等打包一起共享；Skill 是流程本体。Plugin 回答"怎么分发"，Skill 回答"单个任务怎么执行"。

常见误区速查

  • 误区：SKILL.md 越长越好、把整本手册塞进去。正解：SKILL.md 越短越好（规范建议 <500 行），细节放引用文件；Skill 是为了省上下文，不是往上下文里塞更多东西。
  • 误区：装了 Skill 就等于永久占用大量上下文。正解：触发前每个 Skill 只占元数据（约 100 token），靠渐进式披露按需加载。
  • 误区：一有重复需求就做 Skill。正解：若团队还没搞清流程，过早封装只会"把混乱变成可复用的混乱"。先手动跑通、记录步骤、摸清边界，再封装。
  • 误区：Skill 能自己连外部实时数据。正解：Skill 是静态流程；访问实时数据要靠 MCP，Skill 不要假装有它从未被授予的实时访问。
